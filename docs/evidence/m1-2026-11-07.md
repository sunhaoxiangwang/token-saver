## Deviations from the approved plan, for review

1. Representation (plan 5.1). The plan assumed clients show the model the text block and placed
   metadata in `structuredContent`. Claude Code 2.1.319 hands the model the `structuredContent` JSON
   and drops the text block when both are present. Sanitized before/after observation, two smoke
   attempts of task T2 in arm B against the same fixture and prompt, outside the comparison:

   | | Before (metadata in `structuredContent`) | After (text only, `#` metadata line) |
   |---|---|---|
   | first `tool_result` the model saw | the 220-byte outline metadata JSON; no listing text | the 1,189-byte listing text with its metadata line |
   | turns / tool calls | 65 / 63 | 4 / 2 |
   | wall time | 156 s | 21 s |
   | total tokens (uncached + cache write + cache read + output) | 288,978 (258 + 38,951 + 237,895 + 11,874) | 68,702 (66 + 13,765 + 54,327 + 544) |
   | correlation | incomplete: client result digests differed from the relay's text digests | complete: 2 of 2 matched |
   | answer | correct | correct |

   The implemented contract returns text only: content lines, the optional
   `[truncated: <stop_reason>]` trailer, and a final `# key=value` metadata line with the fields of
   plan 5.2 to 5.4 (nested keys joined with `.`). No `structuredContent`, no advertised output
   schema; the metadata schemas are kept for tests and documentation. Field names, bounds, and
   semantics are unchanged. Size bound: the metadata line's maximum escaped cost (every integer at
   its widest, every enumeration at its longest) is reserved from the 12,288-byte budget before any
   content unit is admitted, the final serialization is checked exactly, and
   `tests/workspace_contracts.rs` asserts the bound on the review's 120,459-byte escaped-content
   case, on maximum context, on 400-character control-character lines, on 1,024-byte generated
   paths, and on a dense result that fills the budget and refuses the next unit.
2. Outline metadata gains `dirs_unreadable`: a queued directory that cannot be re-resolved from the
   root when visited (moved, removed, or unreadable) is counted there instead of being silently
   skipped. Search counts the same case under `files_skipped.unreadable`.
3. Per-call cache hints (`ttlMs` 0 or 1000 per tool, plan 6) are not implementable: rmcp 3.9.0's
   `CallToolResult` has no cache-hint fields; only `tools/list` and `server/discover` carry them,
   unchanged at `ttlMs: 0`, `cacheScope: private`.
4. Supervision tests S1 to S7 assert detection through the latched cause and termination through
   the end of the serve loop and the recording terminator (the fixture runs in-process, where the
   stderr `fatal` line cannot be captured); the release-binary tests assert stderr events for the
   cases real filesystem objects can produce.

Client facts recorded: `claude -p --max-turns 12` did not bound a 65-turn run; Claude Code's
`PostToolUse` hook does not fire for tool-error results; Codex's `exec --json` reports no model id
and its `mcp_tool_call.result` omits `isError` (the relay's record is authoritative for both).

## Harness corrections during the run (reviewer findings on the harness)

1. F01: `report.py` treated any nonempty cell with usage as resolved. Now a cell is resolved only
   when measured attempt ids 1 to 6 are present exactly once and every one has usage; a missing,
   duplicate, or extra attempt id makes the comparison `unresolved` and no saving can be claimed.
   Regression tests: one attempt per arm; six records with a duplicate attempt 5 and no attempt 6;
   an extra attempt 7; the exact set resolves.
2. F02: the T2 checker accepted an answer that contained the expected substrings while asserting a
   different value ("MAX_OUTBOUND_FRAME_BYTES is 32768 in src/lib.rs. The value 16384 is obsolete").
   Now every decimal number of at least 1,000 and every `.rs` path in the answer count as asserted,
   and the answer is correct only when each set is a singleton holding the right value; a
   contradictory or hedged answer is incorrect. Regression tests include that answer and
   `16384 in src/lib.rs or src/transport.rs`. `checker_version` 2 is recorded in every record and
   report.

3. F03 (found by this project while the run was in progress): the T5 checker's claimed-path
   pattern accepted only `.md` paths while the expected set, derived from the fixture, rightly
   included `docs/evidence/m0/artifact-index.json`, so every T5 answer could score at most 3 of 4
   and was labelled `partial` in all arms of both clients. Now any file below `docs/` is claimable.
   Regression tests include a `.json` path and a list with punctuation. `checker_version` 3.

Regrading. Raw answers are hashed and deleted by design, so attempts already recorded under an
earlier checker version cannot be regraded offline. Every T2 cell was rerun with checker version 2
(the T2 rule is unchanged in version 3) and every T5 cell with checker version 3, both clients, three
arms, seven attempts each, in separate run roots after the fixes; the reported T2 and T5 cells are
the reruns. The original T2 and T5 records are preserved unchanged in
`docs/evidence/m1/compare/original-t2-t5/` (provisional labels under the earlier checker versions)
and summarized in the comparison section. T1, T3, T4, and T6 were not affected and were not rerun;
their checkers were re-read for the same class of defect (T1 precision and recall were 14 of 14 for
every arm of both clients; T3 and T6 are exact comparisons; T4 is strict set equality over bare
name lines).
